# 供应链信息化团队周报系统设计

日期：2026-09-11

## 1. 背景

供应链信息化部门负责协调业务用户与 IT 开发，团队成员同时承担 KPI 项目和 KPI 以外的临时需求。现有周报从 PPT 改为表格后，虽然便于 AI 读取，但仍存在三类问题：

1. KPI 表和周报表没有关联，成员需要重复维护项目基础信息与进度。
2. 周会按成员逐人汇报，但全量表格同时展示大量本周无变化的项目，信息密度高且不直观。
3. 周报表将任务基础信息、每周进展和 `W37-*` 等周次字段混在一起，随着周次增加会持续变宽，不利于填写、查询和 AI 总结。

## 2. 设计目标

- KPI 表字段结构保持完全不变。
- KPI 项目与非 KPI 事项进入统一事项体系。
- 成员只在 WPS 多维表格中填写一次周报；KPI 项目的最新进度自动回写 KPI 表。
- 周报历史按“记录行”纵向积累，不再按周次新增字段。
- 当周没有周报记录的任务不出现在 HTML 汇报页。
- 周会按成员逐人汇报；多人参与同一项目时，各自的不同关键任务独立展示。
- AI 只生成团队管理摘要，不改写成员原始内容。
- 第一版在周会电脑本地运行，不建设多人访问的 Web 填写系统。

## 3. 第一版范围

### 3.1 包含

- 三张 WPS 多维表格：KPI 表、事项台账、周报记录表。
- 周报填报表单、非 KPI 事项新增表单及必要的 WPS 视图。
- 周报提交后更新事项台账，并将 KPI 事项的最新进度回写 KPI 表。
- 本地 HTML 汇报应用。
- 公司内部、兼容 OpenAI API 的大模型接入。
- 实时团队摘要、周会前最终摘要及按成员逐页展示。
- 周报历史查询、同步异常提示和逻辑锁定。

### 3.2 不包含

- 成员使用 HTML 填写周报。
- 登录、单点登录或成员级应用权限控制。
- 公网或公司内网部署。
- 独立的周报快照表。
- 基于计划偏差自动推导灯光。
- 自动生成或跟踪周会行动项。

现有目录中的 WPS 周会 Excel 示例及“周会行动项”设计不属于本规格的第一版交付范围。

## 4. 总体架构

```text
成员
  ↓ WPS表单填报
周报记录表
  ↓ WPS自动化或AirScript
事项台账 ──→ KPI表（仅更新既有字段）

周报记录表
  ↓ WPS开放接口读取
周会电脑上的本地服务
  ├─→ 公司内部大模型：生成团队摘要
  └─→ HTML汇报页：摘要首页＋成员逐页汇报
```

WPS 多维表格是业务数据的唯一来源。本地应用不承担成员填报，不保存第二份项目或周报数据库；它只负责读取数据、调用内部模型、保存 AI 摘要记录和提供投屏页面。

浏览器页面不得直接持有 WPS 或大模型密钥。所有密钥和外部接口调用由本地服务处理，配置文件不得提交到版本库或展示在页面中。

## 5. 数据模型

### 5.1 KPI 表

KPI 表保持现有结构、字段名称和字段顺序不变：

`项目集、项目名称、关键任务、主要内容、优先级、优化流程数量、优化系统功能点、项目收益（预估收益 验收实际收益）、单项责任人、当前状态、完成比例、计划比例、灯光、进度说明、实际上线时间、对应痛点码、计划开始时间、计划完成时间、IT产品Owener、IT开发、涉及系统、阶段（plan actual）`

约束：

- 一条 KPI 行视为一个独立关键任务，也是事项映射的最小粒度。
- 不增加业务字段或技术 ID 字段。
- 使用 WPS 内部记录 ID 建立外部映射；内部记录 ID 不视为 KPI 表结构变更。
- 只允许自动回写 `当前状态、完成比例、灯光、进度说明` 四个既有字段。
- KPI 行被删除并重新创建时，内部记录 ID 会变化，必须进入异常视图由维护人员重新关联。

### 5.2 事项台账

事项台账统一管理 KPI 与非 KPI 事项，并保存事项当前状态。

| 字段 | 类型 | 说明 |
|---|---|---|
| 事项ID | 自动编号 | 稳定的业务关联标识 |
| 事项类型 | 单选 | KPI项目、非KPI需求、临时任务 |
| KPI记录ID | 单行文本 | KPI事项对应的 WPS 内部记录 ID；非KPI为空 |
| 项目集 | 单行文本 | KPI同步或非KPI人工填写 |
| 项目名称 | 单行文本 | KPI同步或非KPI人工填写 |
| 任务名称 | 单行文本 | KPI的关键任务或非KPI任务名称 |
| 任务内容 | 多行文本 | 工作范围与说明 |
| 业务价值点 | 多行文本 | 预期业务价值 |
| 任务级别 | 单选 | 沿用部门现有定义 |
| 优先级 | 单选 | 沿用部门现有定义 |
| 计划开始时间 | 日期 | 基础计划 |
| 计划完成时间 | 日期 | 基础计划 |
| 责任人 | 成员/单选 | 周会归组依据 |
| 业务接口人 | 成员/文本 | 基础信息 |
| IT接口人 | 成员/文本 | 基础信息 |
| 当前状态 | 单选 | 未开始、进行中、暂停、已完成 |
| 当前完成比例 | 百分比 | 最新实际进度 |
| 最新进度说明 | 多行文本 | 最近一次周报的主要进展 |
| 数据来源 | 单选 | KPI同步、人工创建 |
| 是否有效 | 复选/单选 | 在途、已关闭、已归档 |
| 最后同步时间 | 日期时间 | 系统维护 |

KPI 事项由系统映射，不要求成员重复维护基础信息。非 KPI 事项通过独立 WPS 表单创建一次，之后与 KPI 事项使用同一套周报流程。

首次映射可用 `项目集＋项目名称＋关键任务＋单项责任人` 生成候选关系，但最终保存 KPI 内部记录 ID。出现重复组合或记录 ID 失效时，不自动猜测，必须人工确认。

### 5.3 周报记录表

周报记录表既保存成员任务进展，也保存每周 AI 团队摘要。

| 字段 | 类型 | 说明 |
|---|---|---|
| 周报记录ID | 自动编号 | 唯一记录标识 |
| 记录类型 | 单选 | 任务进展、团队摘要 |
| 周报周期 | 单行文本/周次 | 例如 `2026-W37` |
| 关联事项 | 关联记录 | 关联事项台账；团队摘要记录为空 |
| 当周项目名称 | 单行文本 | 提交时从事项台账复制，用于还原历史周会内容 |
| 当周任务名称 | 单行文本 | 提交时从事项台账复制，用于还原历史周会内容 |
| 当周事项类型 | 单选/文本 | 提交时从事项台账复制 |
| 责任人 | 成员/文本 | 从关联事项带出并保存，作为成员汇报归组依据 |
| 当周计划完成时间 | 日期 | 提交时从事项台账复制并保存 |
| 更新类型 | 单选 | 常规进展、里程碑、风险、延期、上线、验收 |
| 本周主要进展 | 多行文本 | 任务记录为成员原文；摘要记录为本周关键成果 |
| 当前完成比例 | 百分比 | 当周实际进度快照 |
| 当周计划比例 | 百分比 | 提交时从 KPI/事项台账复制，不做动态引用 |
| 进度偏差 | 公式 | 当前完成比例减当周计划比例 |
| 本周状态 | 单选 | 未开始、正常、有风险、需协同、暂停、已完成 |
| 存在问题 | 多行文本 | 任务问题；摘要记录为团队风险 |
| 需要帮助 | 多行文本 | 可为空；建议包含事项、协助方和期望时间 |
| 下周计划 | 多行文本 | 任务计划；摘要记录为团队下周重点 |
| 更新时间 | 日期时间 | 系统维护 |
| 锁定状态 | 单选 | 编辑中、逻辑锁定、逾期修改 |
| KPI同步状态 | 单选 | 不适用、待同步、同步成功、同步失败 |
| KPI同步时间 | 日期时间 | 最近成功回写时间 |
| KPI同步错误 | 多行文本 | 仅异常视图展示 |
| AI摘要状态 | 单选 | 不适用、生成中、草稿、最终版、生成失败、可能过期 |
| AI生成时间 | 日期时间 | 最近一次成功生成时间 |
| AI模型 | 单行文本 | 保存生成最终摘要时的模型标识 |
| AI来源记录ID | 多行文本 | 团队摘要引用的任务进展记录 ID 列表 |

唯一性规则：

- 任务进展：`周报周期＋关联事项` 唯一，同一事项同一周只有一条记录。
- 团队摘要：`周报周期＋记录类型=团队摘要` 唯一，每周只有一条。
- 截止前重复提交应更新原记录，不得新增重复记录。
- 历史记录永久保留，不用下一周数据覆盖上一周。
- 某事项在某周没有记录，含义仅为“没有提交当周进展”；HTML 当周汇报不展示该事项，也不自动生成虚假记录。

## 6. WPS 填报与视图

### 6.1 周报填报表单

表单仅向成员展示需要输入的字段：

1. 关联事项；
2. 更新类型；
3. 本周主要进展；
4. 当前完成比例；
5. 本周状态；
6. 存在问题；
7. 需要帮助；
8. 下周计划。

周报周期、当周计划比例、责任人、同步状态、锁定状态等由系统设置。表单中“需要帮助”的提示语为：

> 请说明需要协调的事项、期望协助方和期望解决时间。例如：需要数据平台组在9月15日前提供供应商主数据接口。

### 6.2 非 KPI 事项表单

非 KPI 事项先通过事项台账的独立表单创建，至少填写项目名称、任务名称、任务内容、业务价值点、优先级、计划日期和责任人。创建后立即可在周报表单中选择。

### 6.3 建议视图

- 本周已填记录：当前周、记录类型为任务进展。
- 我的历史：按责任人及周次筛选。
- 同步异常：KPI同步状态为待同步或同步失败。
- 非KPI在途事项：事项类型不是 KPI 且状态未完成。
- 团队摘要历史：记录类型为团队摘要。

## 7. 提交、回写与状态映射

提交顺序必须保证周报优先保存：

1. 新建或更新当周任务进展记录。
2. 更新事项台账的当前状态、当前完成比例和最新进度说明。
3. KPI 事项回写 KPI 表四个字段。

状态映射如下：

| 周报状态 | KPI当前状态 | KPI灯光 |
|---|---|---|
| 未开始 | 未开始 | 绿 |
| 正常 | 进行中 | 绿 |
| 有风险 | 进行中 | 黄 |
| 需协同 | 进行中 | 红 |
| 暂停 | 暂停 | 黄 |
| 已完成 | 已完成 | 绿 |

`本周主要进展`覆盖 KPI 的`进度说明`，因为完整历史保存在周报记录表中。第一版不根据计划偏差自动改变灯光。

回写应采用幂等设计：相同周报记录被重复处理时，只更新对应 KPI 行，不创建额外事项或周报。回写失败时，周报记录保留并标记“同步失败”；自动重试不得覆盖成员提交内容。

## 8. 截止与逻辑锁定

截止时间按周配置。截止前同一事项的当周记录可以反复修改；截止后标记为“逻辑锁定”。

第一版不做成员身份和行级权限控制，因此逻辑锁定不能阻止拥有 WPS 编辑权限的成员直接修改单元格。截止后的修改必须：

- 标记为“逾期修改”；
- 不自动回写 KPI，除非维护人员确认后重新同步；
- 将已经生成的最终 AI 摘要标记为“可能过期”；
- 在 HTML 页面显示明显提示。

真正禁止截止后编辑属于后续权限版本，可通过 WPS 原生权限或应用层身份控制实现。

## 9. AI 摘要

### 9.1 输入与输出

AI 只读取当前周、记录类型为“任务进展”的记录，并按责任人组织结构化 JSON。AI 不读取全量 KPI 表，也不改写成员原文。

固定输出四部分：

1. 本周关键成果；
2. 风险与问题；
3. 需要协调；
4. 下周重点。

每条摘要必须带来源周报记录 ID，以便页面定位到成员及具体任务。

### 9.2 生成规则

- 只能依据成员填写内容，不补充或推测事实。
- 没有“需要帮助”内容时，不自行制造协调诉求。
- 多人参与同一项目时，仍按各自关键任务处理，不擅自合并责任。
- 内容过多时优先保留里程碑、风险、延期、上线、验收和协同事项。
- AI 输出为空、格式错误或调用失败时，不覆盖上一版成功摘要。

### 9.3 实时与最终版

“实时”限定为本地汇报应用运行期间：应用轮询 WPS 的更新时间，发现任务进展变化后等待约一分钟再重新生成草稿，避免连续编辑造成重复调用。

周会前由负责人点击“生成最终版”，系统基于当时全部任务进展重新生成并保存当周团队摘要记录。后续数据发生变化时，最终版不静默改变，只标记为“可能过期”，由负责人决定是否重新生成。

内部模型通过兼容 OpenAI API 的适配器调用。配置包含接口地址、模型名称、访问密钥、超时时间和最大输入长度。模型适配器与 WPS 数据访问模块相互独立，便于后续更换模型。

## 10. HTML 汇报页

### 10.1 摘要首页

首页展示：

- 周报周期和数据更新时间；
- AI 摘要生成时间及草稿/最终版/可能过期状态；
- 本周关键成果；
- 风险与问题；
- 需要协调；
- 下周重点。

点击摘要条目可以跳转到对应成员和任务。

### 10.2 成员汇报页

- 一级结构按责任人组织，一人一页。
- 顶部提供成员标签及上一位、下一位切换。
- 每位成员只展示当前周有任务进展记录的事项。
- 每张任务卡显示项目名称作为上下文、关键任务名称、事项类型、完成比例、本周状态、本周主要进展、存在问题、需要帮助和下周计划。
- 风险和需要帮助使用醒目标识。
- 多名成员参与同一项目时，各自的不同任务显示在各自页面，不做项目级合并。
- 当周没有提交任何任务进展的成员可在成员导航中隐藏，或以“本周无汇报”状态置于末尾；第一版默认隐藏。

## 11. 模块边界

本地应用划分为以下独立模块：

- WPS 数据适配器：读取表结构和记录、保存团队摘要、处理分页和重试。
- 周次服务：计算当前周、截止时间、逻辑锁定和逾期状态。
- 数据整理器：过滤当前周任务进展并按责任人归组。
- AI 适配器：调用内部 OpenAI 兼容接口并验证结构化输出。
- 摘要服务：管理草稿、最终版、可能过期和来源记录。
- 汇报界面：摘要首页、成员导航和任务卡片。
- 配置模块：保存非敏感配置；敏感密钥从本地安全配置或环境注入。

各模块通过明确的数据对象交互。WPS 或 AI 接口替换不应要求修改汇报页面的业务组件。

## 12. 异常与降级

- WPS读取失败：页面显示明确错误和重试入口，不展示可能被误认为最新的空周报。
- WPS写入团队摘要失败：保留本地生成结果供当前会议查看，同时标记“未保存至WPS”。
- KPI回写失败：周报记录不丢失，进入同步异常视图并自动重试。
- AI失败：成员原始周报仍可正常汇报；保留上一版摘要并标记“可能过期”。
- AI输出格式错误：执行一次纠正重试；仍失败则采用 AI 失败降级流程。
- 重复记录：按唯一性规则阻止或合并，不允许 HTML 同时展示同一事项同一周的两条进展。
- KPI映射冲突：不自动猜测，进入人工处理队列。
- 输入过长：按任务边界分批总结，再汇总为团队摘要，并保留来源记录 ID。

## 13. 可行性门槛

正式开发前先完成 WPS 读写验证：

1. 确认能创建或获得企业应用/用户授权。
2. 申请多维表格读写权限。
3. 读取目标文件表结构。
4. 分页读取测试记录。
5. 更新一条测试记录并验证字段类型。
6. 验证表单视图、关联字段、自动化或 AirScript 在当前 WPS 租户中可用。

验证失败时不进入正式开发。若企业应用权限暂时不可得，可评估将 AirScript 令牌放在本地服务端作为过渡方案；令牌不得放入 HTML 或浏览器存储。

## 14. 验收标准

- KPI 表的字段、名称和顺序未被改变。
- KPI 的每条关键任务能唯一映射到一个事项。
- 非 KPI 事项只需创建一次，之后能正常填写周报。
- 同一事项同一周重复提交只更新原记录。
- 周报记录可以按事项还原跨周历史进度。
- 当前周没有记录的事项不出现在汇报页。
- 汇报页按成员逐页展示，多人同项目的任务不被合并。
- 周报提交后，事项台账和 KPI 四个字段按规则更新。
- 状态与灯光映射结果符合设计表。
- KPI回写失败不会丢失周报，并能在异常视图中识别和重试。
- AI摘要只包含四个约定部分，并能定位来源记录。
- AI失败时仍能使用原始周报完成会议汇报。
- 最终摘要之后发生的数据变化会显示“可能过期”。
- 本地浏览器和静态资源中不包含 WPS 或模型密钥。
- 第一版逻辑锁定与逾期修改标记符合规则。

## 15. 实施顺序

1. WPS 接口和租户能力验证。
2. 配置三张表、关联字段、表单和视图。
3. 建立 KPI 到事项台账的初始化映射及异常处理视图。
4. 实现周报提交后的事项更新、KPI回写和重试机制。
5. 实现本地 WPS 数据读取与按成员整理。
6. 实现内部模型适配、实时草稿和最终摘要。
7. 实现摘要首页与成员逐页汇报。
8. 使用少量真实项目试运行一至两个周次。
9. 根据试运行结果调整字段说明、摘要提示词和展示密度。

# 供应链信息化团队周报系统实施计划

日期：2026-09-11  
依据：[供应链信息化团队周报系统设计](../specs/2026-09-11-supply-chain-weekly-report-design.md)

## 1. 计划目标

交付一套以 WPS 多维表格为唯一业务数据源的周报系统：成员在 WPS 填写任务进展，系统自动更新事项台账并回写 KPI 表；周会电脑运行本地应用，调用公司内部大模型生成团队摘要，并按成员逐页展示本周有更新的任务。

第一阶段严格遵守以下边界：

- 不改变 KPI 表结构。
- 不开发成员 HTML 填写工作台。
- 不开发登录和成员级权限控制。
- 不部署到公网或公司内网。
- 不增加独立快照表或周会行动项表。
- WPS 能力验证未通过前，不进入正式开发。

## 2. 默认技术选型

在没有既有应用代码约束的前提下，建议采用：

- 本地服务：Node.js 20+、TypeScript、Express。
- 页面：原生 HTML、CSS、TypeScript，不引入重量级前端框架。
- 数据校验：Zod 或等价 JSON Schema 校验器。
- 测试：Vitest，接口测试使用本地假 WPS/AI 服务。
- WPS 集成：WPS 开放接口；周报回写优先使用 WPS 原生自动化，能力不足时使用 AirScript。
- AI 集成：OpenAI 兼容 HTTP 接口，模型和地址均由本地配置提供。

选择原则是减少本地安装和运行复杂度，同时把 WPS、AI、业务规则和页面分开，避免未来更换接口时重做整个应用。

## 4. 阶段零：WPS 可行性门槛

### 任务 0.1：确认授权路径

目标：明确当前 WPS 租户能否让本地服务读取和更新多维表格。

操作：

1. 联系 WPS 管理员确认能否创建企业自建应用或获得用户授权。
2. 申请多维表格读写权限。
3. 明确是否启用了接口签名、IP 白名单和数据权限审核。
4. 为验证准备一份非生产测试多维表格，禁止直接使用正式 KPI 数据做写入实验。

产出：

- 授权方式说明；
- 测试文件 ID；
- 凭证保存位置说明；
- 已批准的读写范围。

通过标准：本地服务可以获得有效访问令牌，并被授权访问测试文件。

### 任务 0.2：完成最小读写验证

目标：用最小脚本证明接口真实可用。

验证顺序：

1. 获取测试多维表格的文件与数据表结构。
2. 分页读取记录。
3. 创建一条测试记录。
4. 更新该测试记录的普通文本、单选和百分比字段。
5. 读取更新结果并核对字段类型。
6. 验证关联记录字段能否通过接口可靠读写。
7. 验证表单视图是否可创建和配置必填字段。
8. 验证当前租户可用的自动化触发器；若不足，再验证 AirScript。

测试要求：

- 密钥不能写入脚本或提交到文件。
- 每一步记录请求结果、错误码和所需权限。
- 不对正式 KPI 表执行写入。

通过标准：读取、创建、更新和关联记录均成功，且至少一种自动回写机制可用。

### 门槛决策

- 全部通过：进入阶段一。
- 企业应用不可用但 AirScript 令牌可用：评估过渡方案后由用户确认再继续。
- 无可靠写入方式：停止开发，仅保留 WPS 手工填报与静态汇报方案，不假设自动回写可实现。

## 5. 阶段一：配置三张 WPS 表

### 任务 1.1：核对 KPI 表

1. 读取 KPI 表字段名称、顺序和字段类型。
2. 与设计文档中的字段清单逐项比对。
3. 记录 `当前状态、完成比例、灯光、进度说明` 四个回写字段的实际字段 ID 和数据格式。
4. 确认 WPS 内部记录 ID 在读取后稳定可用。

验收：未对 KPI 表增加、删除、改名或调整任何字段。

### 任务 1.2：创建事项台账

按照设计文档创建事项台账字段，重点配置：

- 事项ID为自动编号；
- 事项类型为单选；
- KPI记录ID为系统维护字段；
- 当前状态选项为未开始、进行中、暂停、已完成；
- 是否有效区分在途、已关闭、已归档；
- 责任人为周会归组字段。

创建“新建非KPI事项”表单，仅展示成员需要填写的业务字段。系统字段和同步字段隐藏。

### 任务 1.3：创建周报记录表

按照设计文档创建全部业务字段和系统字段。必须配置：

- 记录类型：任务进展、团队摘要；
- 关联事项：关联事项台账；
- 本周状态：未开始、正常、有风险、需协同、暂停、已完成；
- 同步状态和 AI 摘要状态选项；
- 进度偏差公式；
- 团队摘要允许关联事项为空。

创建以下视图：

- 周报填报表单；
- 本周已填记录；
- 我的历史；
- 同步异常；
- 团队摘要历史。

表单只展示九个已批准的成员输入字段，并为“需要帮助”设置填写提示。

### 任务 1.4：建立唯一性检查

WPS 表单可能无法天然强制复合唯一键，因此通过自动化或 AirScript 检查：

- 任务进展唯一键：周报周期＋关联事项；
- 团队摘要唯一键：周报周期＋记录类型。

发现重复时：

- 截止前将新提交内容合并到原记录；
- 不生成第二条有效任务进展；
- 无法安全合并时标记异常，等待人工处理。

验收：同一事项同一周重复提交不会在 HTML 中出现两张任务卡。

## 6. 阶段二：KPI映射与自动回写

### 任务 2.1：初始化 KPI 事项映射

1. 扫描 KPI 表全部记录。
2. 用 `项目集＋项目名称＋关键任务＋单项责任人` 生成候选匹配键。
3. 为每条无冲突 KPI 记录创建或更新事项台账记录。
4. 在事项台账保存 KPI 内部记录 ID。
5. 对重复候选键、缺少关键字段或失效记录 ID 生成异常清单，不自动猜测。

验收：每条有效 KPI 行唯一对应一个事项；重复或缺失数据有明确人工处理入口。

### 任务 2.2：实现状态和灯光映射

实现并测试固定映射：

| 周报状态 | KPI当前状态 | KPI灯光 |
|---|---|---|
| 未开始 | 未开始 | 绿 |
| 正常 | 进行中 | 绿 |
| 有风险 | 进行中 | 黄 |
| 需协同 | 进行中 | 红 |
| 暂停 | 暂停 | 黄 |
| 已完成 | 已完成 | 绿 |

第一版不得根据进度偏差另行修改灯光。

### 任务 2.3：实现周报提交处理

每次处理遵循固定顺序：

1. 确认任务进展记录已保存。
2. 将当周计划比例复制到周报记录，形成历史快照值。
3. 更新事项台账当前状态、完成比例和最新进度说明。
4. 若为 KPI 事项，更新 KPI 表的当前状态、完成比例、灯光和进度说明。
5. 写入 KPI 同步状态、同步时间和错误信息。

幂等要求：相同周报记录被重复触发，只更新同一事项和 KPI 行，不新增重复记录。

### 任务 2.4：实现重试和逻辑锁定

- KPI 回写失败时保留周报，状态改为同步失败。
- 对可恢复错误执行有限次数退避重试。
- 权限不足、字段不存在、映射冲突等错误不无限重试。
- 截止后修改标记为逾期修改，不自动回写 KPI。
- 逾期修改后，将对应周次的最终摘要标记为可能过期。

验收：任何回写失败都不会删除或覆盖成员周报原文。

## 7. 阶段三：本地汇报服务基础

### 任务 3.1：创建最小本地应用

1. 初始化独立 Node.js/TypeScript 项目。
2. 添加配置校验和启动错误提示。
3. 服务仅绑定 `127.0.0.1`，不向局域网或公网开放。
4. 提供健康检查接口和静态页面入口。
5. 提供 `.env.example`，但不创建包含真实密钥的示例值。

验收：一条本地启动命令可以打开空汇报页面；缺少配置时给出明确说明，不泄露密钥。

### 任务 3.2：实现 WPS 数据适配器

支持：

- 访问令牌和可选接口签名；
- 表结构读取；
- 记录分页读取；
- 条件过滤后的内存归一化；
- 团队摘要记录创建或更新；
- 超时、限频和短暂网络故障重试；
- WPS 错误码转换为可理解的本地错误。

适配器输出统一领域对象，页面和 AI 模块不得直接依赖 WPS 原始字段格式。

### 任务 3.3：实现周次与数据整理

- 按 Asia/Shanghai 时区计算 ISO 周次。
- 支持从页面选择历史周次。
- 过滤记录类型为任务进展且周报周期等于所选周次的数据。
- 没有当周记录的任务完全排除。
- 按责任人归组；同项目的不同关键任务保持独立。
- 第一版隐藏没有任何当周进展的成员。

验收：给定固定测试数据，成员顺序、任务数量和周次过滤结果可重复验证。

## 8. 阶段四：AI摘要

### 任务 4.1：定义结构化输入和输出

AI 输入包含：

- 周报周期；
- 责任人；
- 周报记录ID；
- 项目名称和任务名称；
- 更新类型、状态和进度比例；
- 本周主要进展、存在问题、需要帮助、下周计划。

AI 输出固定为：

- 本周关键成果；
- 风险与问题；
- 需要协调；
- 下周重点。

每条输出必须包含来源周报记录 ID。使用运行时 Schema 校验模型输出，禁止页面直接渲染未经校验的结果。

### 任务 4.2：实现内部模型适配器

- 支持自定义 Base URL、模型名和密钥。
- 兼容 OpenAI API 消息格式。
- 设置请求超时和最大输入长度。
- 对格式错误仅执行一次纠正重试。
- 日志不得输出完整周报正文或访问密钥。

### 任务 4.3：实现草稿与最终版

- 本地应用运行期间轮询 WPS 更新时间。
- 检测到数据变化后等待约一分钟，合并连续修改后生成草稿。
- 页面提供立即刷新和重新生成入口。
- 周会前点击“生成最终版”，重新读取全部当周记录后生成。
- 最终版保存到当周唯一的团队摘要记录。
- 后续数据变化只标记可能过期，不静默替换最终版。

### 任务 4.4：实现AI失败降级

- AI不可用时仍返回成员原始周报数据。
- 上一版有效摘要存在时继续展示，并标记可能过期。
- 空结果或无效结果不得覆盖上一版摘要。
- 输入超长时按任务边界分批总结，再生成团队摘要；所有来源 ID 必须保留。

## 9. 阶段五：HTML汇报页面

### 任务 5.1：实现摘要首页

展示：

- 当前周次；
- WPS 数据更新时间；
- AI 生成时间和状态；
- 四个摘要部分；
- 生成最终版、重新生成和刷新数据按钮。

摘要条目点击后跳转到来源成员和任务。

### 任务 5.2：实现成员逐页汇报

使用已批准的“一人一页切换”布局：

- 顶部成员标签；
- 上一位、下一位；
- 当前成员任务数量及风险/协同数量；
- 每项任务独立卡片；
- 项目名称作为上下文，关键任务作为主标题；
- 展示完成比例、状态、四段原文和事项类型；
- 风险、需要帮助和逾期修改使用醒目标识。

### 任务 5.3：完成投屏可用性

- 支持键盘左右键切换成员。
- 支持全屏展示。
- 在常见 16:9 会议屏幕上无需横向滚动。
- 内容过长时允许任务卡内部展开，不让整页失控。
- 数据为空、网络异常、AI失败和摘要过期均有明确状态页面。

## 10. 阶段六：测试与验收

### 任务 6.1：单元测试

覆盖：

- 周次计算和时区边界；
- 复合唯一键；
- 状态和灯光映射；
- 逻辑锁定与逾期判断；
- 按周次过滤；
- 按责任人归组；
- AI 输出 Schema 校验；
- 摘要过期判定。

### 任务 6.2：集成测试

使用本地假 WPS 和假 AI 服务覆盖：

- WPS 分页、限频、超时和令牌失效；
- 周报读取与团队摘要保存；
- AI正常、超时、空输出和格式错误；
- KPI回写成功、部分失败和重试；
- 重复触发的幂等性。

### 任务 6.3：验收场景

至少准备以下真实形态的脱敏数据：

1. 一个成员负责多个 KPI 和非 KPI 任务，仅部分任务当周更新。
2. 两名成员参与同一项目，但负责不同关键任务。
3. 一个事项跨三周有进展，中间一周没有记录。
4. 有风险、需协同、暂停和已完成任务。
5. KPI回写失败但周报保存成功。
6. AI失败但成员原文正常展示。
7. 最终摘要生成后发生逾期修改。

逐项对照设计文档第14节验收标准签字确认。

### 任务 6.4：安全检查

- 搜索构建产物、浏览器资源和日志，确认不存在 WPS 或 AI 密钥。
- 确认本地服务只监听回环地址。
- 确认错误信息不展示认证头或完整敏感响应。
- 确认真实周报正文不会被写入调试日志。

## 11. 阶段七：试运行与交接

### 任务 7.1：小范围试运行

选择少量成员和真实项目运行一至两个周次，观察：

- 成员能否正确选择关联事项；
- 是否出现重复记录；
- KPI回写准确率；
- AI摘要是否遗漏重点或产生推测；
- 一人一页的现场汇报节奏；
- 页面信息密度和字体是否适合会议屏幕。

### 任务 7.2：修订配置

试运行后只优先调整：

- 表单字段说明；
- 摘要提示词；
- 状态颜色；
- 成员排序；
- 页面默认展开规则；
- 可恢复错误的重试次数。

不在试运行阶段扩展登录、多人 Web 填写或行动项管理。

### 任务 7.3：交接

交付：

- 本地应用与启动说明；
- WPS 三表字段配置说明；
- 表单和视图配置说明；
- WPS 自动化/AirScript 安装说明；
- 内部模型配置说明；
- KPI映射异常和同步失败处理手册；
- 数据备份与恢复说明；
- 验收记录。

## 12. 实施检查点

| 检查点 | 必须满足的条件 | 未满足时 |
|---|---|---|
| G0 WPS能力 | 测试文件读、写、关联和自动化成功 | 停止正式开发 |
| G1 数据结构 | 三表和表单配置完成，KPI结构未变 | 修正后再继续 |
| G2 自动回写 | 幂等、失败保留、状态映射全部通过 | 不接真实KPI |
| G3 本地读取 | 当前周过滤与成员归组准确 | 不接AI和页面 |
| G4 AI摘要 | 结构化输出、来源ID和失败降级通过 | 仅展示原始周报 |
| G5 页面验收 | 投屏、切换、异常状态满足要求 | 不进入试运行 |
| G6 试运行 | 连续一至两个周次无数据丢失 | 不扩大使用范围 |

## 13. 建议实施节奏

按风险排序而不是按页面观感排序：

1. 先证明 WPS 读写与自动化能力。
2. 再完成三表关联和 KPI 回写闭环。
3. 然后开发本地数据读取和成员归组。
